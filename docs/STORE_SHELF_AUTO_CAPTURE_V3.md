# 매대 등록 3.0: 자동 촬영 + 사진 분석

## 1. 흐름

```
매장 선택 → 촬영 시작 → 매대를 천천히 훑기 → 사진 자동 촬영 → (업로드) 서버 분석 → 매대/제품 DB 초안 → 검토 → 게시
```

- 매대 양 끝 지정은 기본 흐름에서 없다(기존 화면은 UserDefaults `GonggiStoreShelfLegacyRecord=true`일 때만, 개발용).
- 제품별 좌표나 칸 번호는 만들지 않는다. 제품은 "어느 매대에 있는지"와 "촬영 당시 보인 수량"만 가진다.
- 고객 검색은 게시된 제품 정보로만 한다: 제품을 찾으면 그 제품이 연결된 매대 앞까지 안내한다.

## 2. 기존 Astra 연동 확인 결과 (코드와 실제 호출)

| 항목 | 확인한 내용 |
|---|---|
| 호출 경로 | `apps/cloud/src/lib/gonggi-advanced-capture/astra-provider.ts`: OpenAI SDK `chat.completions.create` + `image_url`(data URL) + JSON 응답. 360 공간 기록(`gonggi-space-record`)의 이미지 생성은 별도: OpenAI Images API `gpt-image-2` (`images.edit`) |
| 모델 ID | 매장 분석(전체·상세 사진 분석, 보완 확대 읽기)은 공식 API 모델 ID **`gpt-6.1-sol`**을 쓴다. 다른 모델(Astra, gpt-4o)로 자동 대체하지 않는다: 호출이 실패하면 저장 자료를 유지한 채 오류와 다시 시도로 처리한다. 이전에 Astra(`gpt-6-astra`)로 만든 초안은 그 모델의 기존 결과로 남고, 새 촬영과 명시적 재분석만 Sol을 쓴다. 기존 360 공간 기록의 가이드(`GONGGI_ASTRA_MODEL`)는 이 기능이 읽지 않으므로 서로 바뀌지 않는다. 고객의 제품 검색은 서버 모델을 부르지 않는다(기기 안의 이미지 비교) |
| 이미지 입력 | `gpt-6.1-sol`로 이미지(data URL, 1568px 이하) + strict JSON schema + `reasoning_effort`(`low`/`medium`/`high`/`xhigh`; `minimal` 미지원) + `max_completion_tokens`가 동작함을 실제 호출로 확인했다. 응답에는 입력 중 캐시된 토큰과 추론 토큰이 따로 온다(추론 토큰은 출력 토큰에 포함) |
| 인증 | 서버 환경변수 `OPENAI_API_KEY`(길이 164, 앱에는 없음). 앱은 매장 담당자 토큰으로만 서버를 호출하고, 서버가 `StoreShelfManager` 행으로 권한을 검사 |
| 호출 제한 | 기존 Astra: 시간 제한/재시도 없음(실패 시 mock 가이드로 대체). 이번 분석: 요청당 230 s 제한, 요청 최대 2회, 구조 오류 시 수정 요청 1회, 확대 보조 요청 1회, 한 실행의 요청 동시 실행 최대 3개, 세션당 분석 실행 최대 4회. 사진: 앱 촬영 상한 24장, 서버 세션 상한 40장(앱이 더 큰 로컬 세션을 가지면 균등하게 40장만 올리고 전부 기기에 보존), 분석 대상은 한도 안이면 전부 |
| 운영/스테이징 | 이번 분석은 별도 스위치 `STORE_SHELF_ANALYSIS_ENABLED`와 키 `STORE_SHELF_ANALYSIS_OPENAI_API_KEY`를 쓴다. 스테이징에는 이 두 개만 실제 값이고 `OPENAI_API_KEY`와 `GONGGI_ASTRA_ENABLED` 등 다른 기능은 이전처럼 꺼져(더미) 있다 |
| 모델 선택 | 기본·허용 목록 모두 `gpt-6.1-sol`(`STORE_SHELF_ANALYSIS_MODEL`/`_MODELS`). 응답 모델명이 요청과 다르면 실행을 `model_mismatch`로 실패 처리한다. 가격은 공식 가격표(표준, 272K 입력 이하): 입력 $2.00, 캐시 입력 $0.10, 출력 $10.00 / 1M 토큰 |

## 3. 서버 API (모두 매장 담당자 전용, 스테이징)

| 요청 | 설명 |
|---|---|
| `POST /api/gonggi/stores/:id/captures` | 촬영 세션 만들기. `clientSessionId`로 멱등 |
| `POST …/captures/:sid/photos` | 사진 메타(자세 4x4, 내부 파라미터, 추적 상태, 표면 점)와 평면 목록 등록, 업로드 URL 반환(멱등) |
| `POST …/captures/:sid/uploaded` | 업로드된 사진 확인(누락 목록 반환) |
| `POST …/captures/:sid/analyze` | 분석 시작(202). 이미 실행 중이거나 끝난 분석이면 같은 run을 반환 |
| `GET …/captures/:sid` | 상태, 토큰 사용량, 초안(매대, 제품, 관측) |

DB(스테이징 Neon에만 적용, 운영 변경 없음): `StoreCaptureSession`, `StoreCapturePhoto`, `StoreAnalysisRun`(모델, 토큰, 추정 비용, 지연, 시도 횟수, 오류), `StoreCaptureShelf`, `StoreCaptureProduct`, `StoreCaptureObservation`.

## 4. 분석 결과와 규칙

- 모델 응답은 strict JSON schema로 받고 서버가 다시 검증한다. 구조가 맞아도 이름이 맞다는 뜻이 아니므로 `resolver`가 근거 사진/박스를 검사한다.
- 모델의 임시 번호(P1, S1)는 ID로 쓰지 않는다. 같은 이름+맛+용량은 한 상품, 맛/용량이 다르면 별도 상품, 라벨/일부는 제외.
- 읽지 못한 이름은 "제품 N" + 확인 필요로 남긴다. 직접 입력한 이름은 새 촬영이 덮어쓰지 않는다.
- 수량은 "촬영 당시 보인 수량"(`counted` / `lower_bound` / `cannot_count`). 한 사진 안의 별개 구역은 더하고, 여러 사진은 더하지 않고 큰 값만 쓰며(겹침), 가려진 제품은 더하지 않는다. 새 촬영은 이전 관측을 대체하고 합산하지 않는다.
- 화면 문구: "촬영 당시 N개 확인", "수량은 확인되지 않았어요", 마지막 관측 시각. 재고 보장 표현은 없다.

## 5. 매대 공간 위치

- 모델은 사진 속 매대 영역(박스)만 말한다. 거리나 좌표는 쓰지 않는다.
- 서버가 박스 중심의 시선과 촬영 당시 ARKit 정보를 결합한다: 사진마다 카메라 자세, 내부 파라미터, 촬영 중 ARKit이 찾은 **수직 표면(평면)**, 그리고 이미지 중심의 표면 점. 시선이 측정된 평면과 만나는 점이 매대 위치, 평면 법선이 방향이다.
- 두 장 이상이 하나의 전면에 일치하면 "확인됨", 한 장이면 "한 번만 확인됨"(확인 필요), 측정된 표면이 없으면 위치 없음.
- 위치가 없으면 사진, 제품 정보는 초안으로 보존하고 "매대 위치 확인 필요"로 표시한다. 그 매대는 AR 안내 대상이 아니다.
- 보조 절차: 촬영 중 「매대 앞면 확인」(매대 앞면을 비추고 한 번 누르면 그 표면 점을 포함한 사진을 찍는다).
- LiDAR 없이도 동작한다(iPhone 14 Plus 경로: ARKit 평면 감지 + 표면 추정).
- 안내 목적지는 매대 위치에서 고객 쪽으로 0.9 m 앞, 통로 경로는 촬영 중 걸은 궤적으로만 만든다(없으면 직선 방향 표시).

## 6. 자동 촬영 설정 (모두 조정 가능한 시작값, 검증된 기준 아님)

`AutoCaptureConfig`: 최소 간격 0.8 s, 이동 0.25 m 또는 회전 12° 또는 화면 변화 0.12, 최대 속도 0.6 m/s / 0.9 rad/s, 선명도 하한 40(160x120 휘도의 라플라시안 분산), 최근 최대치의 85%, 사진 최대 16장, 내보내기 긴 변 1600 px JPEG 0.85, 이미지 중심 표면 거리 0.3~3.2 m.
촬영 안내 문구(너무 빨라요, 흔들려요, 조금 가까이/뒤로, 추적 중)는 각각 같은 이름의 측정 조건에서만 나온다.

## 7. 비용과 사용량

- 실행마다 토큰과 추정 비용이 `StoreAnalysisRun`에 기록되고 서버 로그에 남는다. 비용은 `STORE_SHELF_ANALYSIS_PRICES`에 설정된 단가로만 계산한다(스테이징: gpt-4o 입력 2.5 / 출력 10 USD per 1M tokens로 설정, 다른 모델은 미설정 → 비용 n/a).
- 상한: 세션당 분석 3회, 요청당 시도 2회, 출력 8,000 토큰, 사진 14장.

## 8. 고객 실시간 검색 설계 (구현 범위: 기기 내 비교, API 보조는 설계만)

1. 기본: 기기 내 이미지 특징 비교 + 포장에서 읽은 글자(이전 빌드와 동일). 호출 비용과 지연이 없다.
2. 불확실할 때만 서버 보조(미구현): 확대 크롭 1장과 후보 제품 최대 5개(이름, 대표 이미지)를 보내 "이 중 어느 제품인가 / 없음"을 묻는다. 호출은 세션당 N회, 최소 간격 3초, 결과가 "없음"이면 미등록으로 처리(가장 비슷한 제품으로 확정하지 않음).
3. 응답 시간을 실제 측정하기 전에는 즉시 인식을 보장하지 않는다. 측정 전에는 UI에서 "확인 중"으로 표시한다.

## 9. 검증 상태

| 구분 | 상태 |
|---|---|
| 실제 API 호출(이미지 입력, strict JSON, 서버 경로) | 확인됨. 합성 매대 사진 2장: gpt-4o 6/6 상품, 중복 0, 가격표를 상품으로 등록하지 않음(스테이징 서버 경로로도 확인) |
| 실사진(냉장고, 편의점) 분석 정확도 | **미검증**: 사진이 아직 없음 |
| 자동 촬영 임계값, 선명도 기준 | **미검증**(실기기 촬영 필요) |
| 매대 공간 위치 정확도, 평면 감지, 복원 후 AR 안내 | **미검증**(실기기) |
| 앱 업그레이드 후 기존 로그인/데이터 유지 | **미검증**(실기기, 아래 확인 절차) |

## 촬영 흐름 (3.0 build 6)
- 전체 사진 1장을 찍은 뒤 분석을 기다리지 않는다. 큰 기본 버튼 "촬영 완료"와 보조 버튼 "가까이 더 찍기"(최대 2장)가 바로 나온다.
- 선택한 사진은 한 번의 최종 분석으로 처리된다. 선행 분석은 없다(같은 전체 사진을 두 번 분석하지 않는다).
- 기기에서는 "명백히 흔들린 사진"만 즉시 다시 찍게 한다(선명도 바닥값). 이름 읽힘이나 제품 누락은 기기에서 판단하지 않는다.
- 최종 분석 후 읽지 못한 부분이 있으면 검토 화면이 해당 구역만 "가까이 더 찍기"로 안내한다. 이 추가 사진은 지도 저장 후의 새 AR 세션에서 찍히므로
  이름과 수량에만 쓰이고 위치 계산에는 쓰이지 않는다(서버가 `x` 접두 좌표계 사진을 위치에서 제외한다).
- 연결이 끊기면 사진은 기기에 남고, "이어서 하기"로 이어서 분석한다.
